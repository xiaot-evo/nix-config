# 高级主题

## Fleet 管理

### 什么是 Fleet

**Fleet** 是在单次管道运行中一起解析的一组主机。Den flake 中声明的所有主机自动形成一个 fleet——它们在共享的作用域树中成为兄弟作用域，`pipe.collect` 可以跨主机收集数据。

### 自定义实体类型

默认情况下，所有主机在同一系统下是兄弟作用域。但如果需要不同的分组——例如将主机分为生产环境和预发环境——可以定义 fleet 实体：

```nix
# 定义 fleet 策略，在父作用域下分组主机
den.policies.to-fleet = _: [
  (den.lib.policy.resolve.to "fleet" {
    fleet = { name = "production"; };
  })
];

den.policies.fleet-to-hosts = { fleet, ... }:
  lib.concatMap (system:
    lib.concatMap (hostName:
      let host = den.hosts.${system}.${hostName}; in
      [ (den.lib.policy.resolve.to "host" { inherit host; })
        (den.lib.policy.instantiate host)
      ]
    ) (builtins.attrNames (den.hosts.${system} or {}))
  ) (builtins.attrNames (den.hosts or {}));

den.schema.flake.includes = [ den.policies.to-fleet ];
den.schema.fleet.includes = [ den.policies.fleet-to-hosts ];
```

这创建了作用域树：

```
flake
└── fleet {fleet=production}
    ├── host {host=igloo}
    └── host {host=iceberg}
```

`fleet` 实体类型已预注册在 `den.schema` 中——你不需要自己声明。

### 跨主机 pipe.collect

所有主机在同一系统中是兄弟作用域。这是 `pipe.collect` 跨主机工作的关键：

```nix
den.quirks.http-backends = {
  description = "HTTP 后端端点";
};

den.aspects.igloo = {
  http-backends = { addr = "10.0.0.1"; port = 8080; };
};
den.aspects.iceberg = {
  http-backends = { addr = "10.0.0.2"; port = 80; };
};

den.policies.fleet-backends = { host, ... }:
  let inherit (den.lib.policy) pipe; in
  [ (pipe.from "http-backends" [
      (pipe.collect ({ host, ... }: true))
    ])
  ];

den.schema.host.includes = [ den.policies.fleet-backends ];
```

`pipe.collect` 的谓词过滤要收集的兄弟作用域。实体类型匹配是自动的——谓词中的必需参数（如 `host`）会对照 schema 实体类型检查。

### Walk-then-Instantiate 架构

所有主机在单次管道遍历中解析。遍历完成后，每个主机的子树从共享状态中提取：

1. **Walk（遍历）**——管道遍历所有实体（flake → 系统 → 主机 → 用户），收集方面、管道数据、路由和实例化请求到作用域分区状态
2. **Pipe assembly（管道组装）**——`assemblePipes` 在遍历后运行，合并暴露的数据并应用 pipe 效果。跨主机 `pipe.collect` 直接从兄弟作用域已遍历的数据中读取
3. **Per-host extraction（每主机提取）**——`applyInstantiates` 将共享状态过滤到每个主机的子树（主机作用域 + 其后代 + 祖先作用域），然后以主机为根作用域重新运行类包装、提供和路由
4. **Instantiation（实例化）**——每个提取的子树传递给 `lib.nixosSystem`、`darwinSystem` 或 `homeManagerConfiguration`

### 作用域树

作用域形成一棵树，由两个扁平映射追踪：

```nix
scopeParent = {
  "" = null;                               # 根
  "system=x86_64-linux" = "";              # 子→父
  "host=igloo" = "system=x86_64-linux";
  "host=igloo,user=tux" = "host=igloo";
};

scopeContexts = {
  "" = {};
  "system=x86_64-linux" = { system = { ... }; };
  "host=igloo" = { system = ...; host = { name = "igloo"; ... }; };
  "host=igloo,user=tux" = { system = ...; host = ...; user = { name = "tux"; ... }; };
};
```

## 作用域划分（Scope Partitioning）

### 作用域身份

每个作用域有一个从其上下文 attrset 计算出的确定性字符串 ID。格式是逗号分隔的 `key=value` 对，按字典排序：

```
{ host = { name = "igloo"; }; user = { name = "tux"; }; }
  → "host=igloo,user=tux"
```

值提取规则：
- 带 `name` 的 attrset：使用 `v.name`
- 字符串：直接使用
- 其他：`<type:key>`（如 `<int:priority>`）

### 父子作用域关系

作用域由 `policy.resolve` 效果创建，形成树结构：

```nix
""                                     ← 根 (flake)
├── "system=x86_64-linux"              ← flake-system
│   ├── "host=igloo"                   ← host
│   │   ├── "host=igloo,user=tux"      ← user
│   │   └── "host=igloo,user=pingu"    ← user
│   └── "host=server"                  ← host
│       └── "host=server,user=admin"   ← user
```

### 分区状态

管道状态字段分为三类：

**作用域分区字段**——每个作用域有自己的分区：

| 字段 | 内容 |
|---|---|
| `scopedClassImports` | 每个作用域按类名键化的类模块 |
| `scopedAspectPolicies` | 遍历中发现的策略 |
| `scopedDeferredIncludes` | 延迟到上下文扩大的包含 |
| `scopedConstraintRegistry` | 每个作用域的约束谓词 |
| `scopedRoutes` | `policy.route` 规格 |
| `scopedInstantiates` | `policy.instantiate` 规格 |

**前缀字段**——带作用域前缀的共享映射：

| 字段 | 键格式 | 目的 |
|---|---|---|
| `seen` | `${scopeId}/${ctxKey}` | 上下文感知的发射去重 |
| `includeSeen` | `${scopeId}/${identity}` | 每个作用域的包含去重 |

**全局字段**——管道范围的值：

| 字段 | 目的 |
|---|---|
| `currentScope` | 活跃作用域 ID——控制哪个分区接收发射 |
| `scopeParent` | 子到父作用域映射 |
| `scopeContexts` | 作用域到上下文映射 |

### 作用域转换

当 `policy.resolve` 效果触发时，管道创建一个新作用域：

1. 丰富上下文——合并 resolve 效果的绑定到当前上下文
2. 计算作用域 ID——`childScopeId = mkScopeId(enrichedCtx)`
3. 去重检查——如果 `childScopeId` 已存在于 `scopeContexts` 中则跳过
4. 记录树——设置 `scopeParent`、`scopeContexts` 和 `currentScope`
5. 安装处理器——`scope.provide` 安装子作用域的实体上下文处理器
6. 遍历实体——解析实体的方面树；所有发射写入 `scopedX.${childScopeId}`
7. 调度策略——触发任何参数现在已满足的策略
8. 恢复——`currentScope` 恢复为父作用域

### 后处理组合

遍历完成后，后处理组合管道状态：

1. 每作用域类导入包装
2. 管道数据组装（暴露 + pipe 效果）
3. 路由应用（`policy.route`）
4. 每主机提取（主机子树 + 祖先）
5. 实例化（`lib.nixosSystem` 等）

祖先作用域在每主机提取中被包含，因为在 flake-system 级别注册的路由和提供必须对主机级解析可见。

## 调试与诊断

### REPL 检查

```console
$ nix repl
nix-repl> :lf .
nix-repl> nixosConfigurations.igloo.config.networking.hostName
"igloo"
```

临时暴露 `den` attrset 作为 flake 输出：

```nix
{ den, ... }: {
  flake.den = den;  # 调试后移除
}
```

然后在 REPL 中检查：

```console
nix-repl> :lf .
nix-repl> den.aspects.igloo
nix-repl> den.hosts.x86_64-linux.igloo
nix-repl> den.policies
```

### PolicyInspect

```nix
den.lib.policyInspect.inspect {
  kind = "host";
  context = { host = den.hosts.x86_64-linux.laptop; };
}
```

返回匹配策略及其目标、路由类型、源/目标实体类型。只调用解析函数，不执行完整管道。

### 跟踪（trace）捕获

在方面中使用 `builtins.trace` 查看上下文：

```nix
den.aspects.laptop.includes = [
  ({ host, ... }@ctx: builtins.trace ctx {
    nixos.networking.hostName = host.hostName;
  })
];
```

或者在任意求值点中断到 REPL：

```nix
({ host, ... }@ctx: builtins.break ctx {
  nixos = { };
})
```

### 手动解析方面

```console
nix-repl> module = den.lib.aspects.resolve "nixos" den.aspects.laptop
nix-repl> config = (lib.evalModules { modules = [ module ]; }).config
```

对于上下文相关的方面，使用主机的 `mainModule`：

```console
nix-repl> module = den.hosts.x86_64-linux.igloo.mainModule
nix-repl> cfg = (lib.nixosSystem { modules = [ module ]; }).config
nix-repl> cfg.networking.hostName
```

### `den.lib.diag` 图库可视化

Diag 是 Den 的诊断库，可以将配置结构可视化为多种格式：

```nix
# 在 REPL 中：
diag = den.lib.diag;
g = diag.hostContext { host = den.hosts.x86_64-linux.laptop; };

# 导出为 Mermaid 图
diag.toMermaid g

# 导出为 PlantUML
diag.toPlantUML g

# 导出为 DOT（Graphviz）
diag.toDOT g

# 导出为 JSON
diag.toJSON g
```

Diag 支持多种视图：

| 视图 | 描述 |
|---|---|
| `diag.hostContext` | 主机的完整方面解析图 |
| `diag.fleet.of` | Fleet 级可视化 |
| `diag.fleet.views` | Fleet 视图选择 |
| `diag.mindmap` | 思维导图风格 |
| `diag.sankey` | Sankey 图 |
| `diag.sequence` | 序列图 |
| `diag.treemap` | 树图 |
| `diag.text` | 文本概览 |

### 常见问题排查

**列表中重复值**：Den 对来自 `den.default` 的 owned 和 static 配置去重，但 `den.default.includes` 中的参数函数在每个上下文阶段运行。写一个带所需上下文参数的裸函数即可。

**缺少属性**：上下文没有预期的参数。用 `builtins.trace` 追踪上下文键。

**错误的类**：检查 `host.class` 是否匹配预期。Darwin 主机的 `class = "darwin"`，不是 `"nixos"`。

**模块未找到**：确保文件在 `modules/` 下且没有 `_` 前缀。

## 代数效应管道（Algebraic Effects）

### nix-effects 库

Den 的解析管道基于 `nix-effects`——一个用于 Nix 的代数效应库。它将依赖注入从隐式内部逻辑提升为形式化、透明的系统。

### FX 发送/绑定

核心概念：效应请求与处理器分离。

```nix
# FX.send：发起请求
fx.send "hostName" null  # "我需要 hostName"

# FX.bind：链式效应计算
fx.bind (fx.send "pkgs" null) (pkgs:
  fx.bind (fx.send "hostName" null) (hostName:
    fx.pure (pkgs.writeText "motd" "Welcome to ${hostName}")))

# FX.bind.fn：自动将函数参数转为效应请求
fx.bind.fn {} ({ pkgs, hostName }: pkgs.writeText "motd" "...")
```

### 管道处理器

处理器响应效应请求：

```nix
fx.handle {
  handlers.hostName = { param, state }: {
    resume = "igloo";   # 处理器决定回答
    inherit state;
  };
  state = {};
} (fx.send "hostName" null)
# => { value = "igloo"; ... }
```

处理器与计算分离意味着相同的函数可以在不同环境中重用以进行测试：

```nix
# 生产环境：真 nixpkgs
fx.handle {
  handlers.pkgs = { ... }: { resume = import <nixpkgs> {}; ... };
  handlers.hostName = { ... }: { resume = "igloo"; ... };
} (fx.bind.fn {} myMotd)

# 测试环境：mock pkgs
fx.handle {
  handlers.pkgs = { ... }: {
    resume = { writeText = name: text: "MOCKED: ${text}"; };
    ...
  };
  handlers.hostName = { ... }: { resume = "test-runner"; ... };
} (fx.bind.fn {} myMotd)
```

### 37 个处理程序详解

Den 的管道实现了 37 个左右的效应处理程序，覆盖：

**上下文处理**（Context Handlers）：
- `scope.provide`——作用域上下文注入
- `scope.currentScope`——当前作用域查询
- `scope.parent`——父作用域访问
- `scope.children`——子作用域枚举

**解析处理**（Resolution Handlers）：
- `resolve.entity`——实体解析
- `resolve.policy`——策略调度
- `resolve.include`——包含遍历
- `resolve.exclude`——排除检查

**数据收集**（Data Collection）：
- `emit.classImport`——类模块发射
- `emit.quirk`——Quirk 数据发射
- `emit.route`——路由注册
- `emit.instantiate`——实例化请求

**管道处理**（Pipe Handlers）：
- `pipe.filter`——过滤
- `pipe.transform`——变换
- `pipe.fold`——折叠
- `pipe.for`——替换
- `pipe.collect`——收集
- `pipe.expose`——暴露
- `pipe.to`——定向交付
- `pipe.as`——重命名
- `pipe.withProvenance`——来源追踪

完整的处理程序集合使 Den 能够在一个统一的效应系统中实现策略调度、方面解析、数据收集和输出生成。

## 库模式 vs 框架模式

### 纯 lib 使用（无 flake 模块）

Den 的核心（`default.nix`）是领域无关的。可以在不使用 `den.hosts`/`den.aspects` 机制的情况下直接使用 `den.lib`：

```nix
# 直接使用 den.lib，不需要完整框架
let
  den = import inputs.den { inherit lib; };

  # 定义方面的纯 attrset
  myAspects = {
    web-server = {
      terranix.resource.aws_instance.web = { ami = "ami-12345"; };
      includes = [
        ({ env, ... }: {
          terranix.resource.aws_instance.web.tags.Env = env;
        })
      ];
    };
  };

  # 用自定义上下文解析
  aspect = myAspects.web-server { env = "production"; };
  module = den.lib.aspects.resolve "terranix" [] aspect;
in { ... }
```

### 自定义域（非 OS 配置）

`den.lib` 不假设 NixOS、Darwin 或 Home Manager。可以为任何 Nix 模块系统构建上下文管道：

```nix
# 自定义域示例
{ lib, den, ... }:
let
  aspects = {
    web = {
      config.nginx.enable = true;
      config.port = 8080;
    };
    db = {
      config.postgres.enable = true;
      config.port = 5432;
    };
  };

  # 用自定义类解析
  module = den.lib.aspects.resolve "myapp" [] [
    aspects.web
    aspects.db
  ];
in {
  # 在自定义 evalModules 中使用
  config = (lib.evalModules {
    modules = [ module ];
  }).config;
}
```

### NVF 独立配置示例

Den 提供了 NVF（Nix Vim Framework）独立模板：

```nix
# 独立的 NVF 配置，不需要完整 Den 框架
{ inputs, den, ... }: {
  # 创建 nvf 命名空间
  imports = [ (inputs.den.namespace "nvf" true) ];

  # 配置 Neovim
  nvf.neovim = {
    viAlias = true;
    vimAlias = true;

    config = {
      colorschemes.catppuccin.enable = true;
      options = {
        number = true;
        relativenumber = true;
      };
    };
  };
}
```

### 何时使用什么

| 场景 | 推荐模式 |
|---|---|
| NixOS/Darwin/HM 主机 | 完整框架（`den.hosts`、`den.aspects`、`den.policies`） |
| 自定义 Nix 模块系统（Terranix、NixVim） | 纯库模式 |
| 混合场景 | 框架用于 OS + 库用于其他领域 |
