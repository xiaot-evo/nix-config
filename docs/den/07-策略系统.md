# 策略系统（Policies）

## 策略是什么

**策略（Policy）** 是 Den 中驱动实体遍历和路由的声明式规则。如果说[方面（aspects）](/explanation/aspects/)定义了"某个实体有哪些配置"，那么策略定义了"实体之间如何连接"——它们是实体关系图中的有向边。

一个策略是一个从上下文（context）到效果列表（effects list）的函数：

```nix
den.policies.host-to-users = { host, ... }:
  map (user: policy.resolve.to "user" { inherit host user; })
    (lib.attrValues host.users);
```

策略是**一等公民**——它们注册在 `den.policies` 中，通过包含在 `includes` 列表中来激活。

## 策略 vs 方面

这是 Den 中最重要的概念区分：

| | 策略（Policies） | 方面（Aspects） |
|---|---|---|
| **职责** | 控制拓扑：实体如何连接、上下文如何丰富 | 提供配置：实体有哪些 NixOS/Home Manager 配置 |
| **输出** | 效果（effects）：创建作用域、包含方面、路由数据 | 类模块（class modules）和 quirk 数据 |
| **激活** | 通过 `includes` 或 `den.schema.*.includes` | 通过 `includes` 的方面引用 |
| **执行时机** | 管道遍历时 | 管道遍历中，由策略驱动 |

简单来说：**策略决定谁去哪里，方面决定到了那里做什么。**

## 策略效果（Effects）

策略返回一个**效果列表**，每个效果是一个带有 `__policyEffect` 标签的 attrset。Den 定义了 7 种效果类型：

### `resolve`——创建子作用域

```nix
let inherit (den.lib.policy) resolve; in

# 丰富当前作用域（添加新绑定，不创建新作用域）
resolve { myFlag = true; }

# 创建指定类型的子实体作用域
resolve.to "user" { inherit host user; }

# 共享扇出（shared fan-out）：子作用域不隔离
resolve.shared { inherit host user; }
```

`resolve` 的行为取决于绑定内容：
- 如果绑定的键匹配 `den.schema` 中的实体类型（如 `host`、`user`），则创建**子作用域**
- 如果是非实体键（如 `myFlag`），则**丰富当前上下文**，不创建新作用域

### `include`——引入方面

```nix
let inherit (den.lib.policy) include; in

# 引入一个已定义的方面
include den.aspects.monitoring

# 也可以内联匿名方面
include { nixos.services.nginx.enable = true; }
```

### `exclude`——排除方面

从当前作用域树中移除一个方面：

```nix
let inherit (den.lib.policy) exclude; in

exclude den.aspects.monitoring
```

### `route`——路由类内容

将某个类的内容从一个作用域分区路由到目标类：

```nix
let inherit (den.lib.policy) route; in

route {
  fromClass = "packages";
  intoClass = "flake";
  path = [ "flake" "packages" system ];
  adaptArgs = _: { pkgs = inputs.nixpkgs.legacyPackages.${system}; };
};
```

### `instantiate`——实例化实体输出

请求在管道后实例化一个实体的类内容：

```nix
let inherit (den.lib.policy) instantiate; in

instantiate host
```

实体必须携带 `instantiate`、`intoAttr`、`mainModule` 等元数据。

### `provide`——注入新模块

直接将一个模块交付到目标类，绕过树遍历：

```nix
let inherit (den.lib.policy) provide; in

provide {
  class = "nixos";
  module = { services.foo.enable = true; };
};
```

与 `include` 的区别：`include` 走方面树遍历（有去重、约束、参数分发），`provide` 直接注入。

### `pipe`——管道转换

连接 quirk 数据流的变换阶段（详见[管道与 Quirks](./08-管道与quirks.md)）：

```nix
let inherit (den.lib.policy) pipe; in

pipe.from "firewall" [
  (pipe.filter (e: e.proto == "tcp"))
  (pipe.transform (e: { port = e.port; }))
]
```

## 策略定义

策略定义在 `den.policies` 下：

```nix
{ lib, den, ... }: {
  den.policies.my-policy = { host, ... }: [
    (den.lib.policy.resolve { myFlag = true; })
  ];
}
```

策略函数的参数签名决定了它何时触发。Den 通过 `lib.functionArgs` 检查当前上下文是否满足所有必需参数：

```nix
# 只在 host 存在时触发
den.policies.host-only = { host, ... }: [ ... ];

# 任何上下文都触发（无参数）
den.policies.always = _: [ ... ];

# 需要 host 和 user 同时存在
den.policies.per-user = { host, user, ... }: [ ... ];
```

## 内置策略

### 核心策略：host-to-users

这是最基本的策略——从主机扇出到用户：

```nix
den.policies.host-to-users =
  { host, ... }:
  let
    aspect = host.aspect;
    forwarded = lib.genAttrs (aspect.__providesForwarded or [ ]) (_: true);
    hasChild = name: builtins.isAttrs aspect && aspect ? ${name} && !(forwarded ? ${name});
  in
  lib.concatMap (
    user:
    [ (resolve.shared { inherit user; }) ]
    ++ lib.optional (hasChild user.name) (include aspect.${user.name})
  ) (lib.attrValues host.users);
```

它自动激活于 `den.schema.host.includes` 中。

### Flake 策略

Flake 策略驱动从 flake 根节点到系统、主机、主机的完整遍历：

```nix
# flake → flake-system：按系统扇出
den.policies.flake-to-systems = _:
  map (system: resolve.to "flake-system" { inherit system; }) den.systems;

# flake-system → host：解析 OS 输出
den.policies.system-to-os-outputs = { system, ... }:
  let hosts = den.hosts.${system} or { }; in
  lib.concatMap (host:
    lib.optionals (host.intoAttr != [ ]) [
      (resolve.to "host" { inherit host; })
      (den.lib.policy.instantiate host)
    ]
  ) (builtins.attrValues hosts);

# flake-system → home：解析 HM 输出
den.policies.system-to-hm-outputs = { system, ... }:
  let homes = den.homes.${system} or { }; in
  lib.concatMap (home:
    lib.optionals (home.intoAttr != [ ]) [
      (resolve.to "home" { inherit home; })
      (den.lib.policy.instantiate home)
    ]
  ) (builtins.attrValues homes);

# 类到 flake 输出的路由策略
den.policies.packages-to-flake = mkOutputPolicy "packages";
den.policies.apps-to-flake = mkOutputPolicy "apps";
# ...
```

### Flake-parts 策略

当 flake 中使用 flake-parts 时，额外的策略支持：

```nix
den.policies.system-to-flake-parts = { system, ... }: [
  (den.lib.policy.resolve.to "flake-parts" {
    flake-parts = {
      name = "flake-parts-${system}";
      aspect = { };
    };
  })
];

den.policies.packages-to-flake-parts = _: [
  (den.lib.policy.route {
    fromClass = "packages";
    intoClass = "flake-parts";
    collectSubtree = true;
    path = [ "packages" ];
    adaptArgs = { config, ... }: config.allModuleArgs;
  })
];
```

## 策略激活机制

### 注册 vs 激活

`den.policies` 只是一个**注册表**——定义一个策略不会自动激活它：

```nix
# 仅注册，从不触发
den.policies.my-policy = { host, ... }: [
  (den.lib.policy.resolve { flag = true; })
];

# 激活——加入 includes 列表
den.schema.host.includes = [ den.policies.my-policy ];
```

### 激活层级

策略可以在任何层级激活：

| 层级 | 位置 | 作用范围 |
|---|---|---|
| 全局 | `den.default.includes` | 所有实体 |
| 按实体类型 | `den.schema.host.includes` | 所有主机 |
| 按方面 | `den.aspects.igloo.includes` | igloo 子树 |
| 内联 | `{ includes = [ ... ]; }` | 包含当前方面 |

### 调度周期

当管道到达一个实体作用域时，策略调度遵循不动点迭代：

1. **收集**——从作用域的 include 链收集所有活跃策略
2. **检查满意度**——通过函数参数签名判断当前上下文是否满足
3. **触发**——调用满足条件的策略，收集效果
4. **丰富**——如果效果添加了新的上下文绑定，合并并排空延迟包含
5. **迭代**——检查新绑定是否满足之前不满意的策略，如果是则重复
6. **收敛**——当没有新策略触发时，发出所有收集的效果

### 自排除不变量

策略不会应用于它自己的输出。源策略名称通过 resolve 链传递，在子作用域中种子化 `firedPolicies`，防止无限递归。

## 策略组合器

### `den.lib.policy.for`——按实体过滤

只在特定实体在上下文中时触发：

```nix
den.schema.host.includes = [
  (den.lib.policy.for den.hosts.x86_64-linux.igloo
    den.policies.igloo-specific)
];
```

匹配使用 `id_hash` 进行健壮的身份比较。接受单个策略或列表：

```nix
den.lib.policy.for entity [
  den.policies.policy-a
  den.policies.policy-b
]
```

### `den.lib.policy.when`——条件门控

只在谓词返回 true 时触发：

```nix
den.schema.host.includes = [
  (den.lib.policy.when ({ host, ... }: host.wsl.enable)
    den.policies.wsl-support)
];
```

### `den.lib.policy.mkPolicy`——创建命名策略

```nix
den.default.includes = [
  (den.lib.policy.mkPolicy "host-guards" myPolicyFn)
];
```

### 组合使用

包装器可以组合：

```nix
den.lib.policy.when (ctx: ctx.flag or false)
  (den.lib.policy.for entity den.policies.my-policy)
```

外层包装器先运行。如果谓词失败，内层包装器不执行。

### 排除的权威语义

父作用域的排除是**权威的**——子作用域不能重新启用被排除的策略：

```nix
parentAspect = {
  excludes = [ den.policies.blocked ];
  includes = [ childAspect ];
};

childAspect = {
  # 这不会重新启用策略！父作用域的排除优先。
  includes = [ den.policies.blocked ];
};
```

这防止了下游方面绕过父作用域建立的安全或正确性约束。

## 策略检查

使用 `den.lib.policyInspect.inspect` 检查哪些策略适用于某个实体以及它们路由到哪里：

```nix
den.lib.policyInspect.inspect {
  kind = "host";
  context = { host = den.hosts.x86_64-linux.laptop; };
}
```

返回匹配的策略集合，包含目标、路由类型和源/目标实体类型。这只调用解析函数，不执行完整管道。

## 完整示例：自定义策略流程

以下示例展示了从定义到激活的完整策略流程：

```nix
# 1. 定义一个 quirk
den.quirks.http-backends = {
  description = "HTTP 后端端点";
};

# 2. 定义一个策略：收集所有主机的后端信息
den.policies.fleet-backends = { host, ... }:
  let inherit (den.lib.policy) pipe; in
  [ (pipe.from "http-backends" [
      (pipe.collect ({ host, ... }: true))
    ])
  ];

# 3. 激活策略（对所有主机）
den.schema.host.includes = [ den.policies.fleet-backends ];

# 4. 主机产生数据
den.aspects.igloo = {
  http-backends = { addr = "10.0.0.1"; port = 8080; };
};
den.aspects.iceberg = {
  http-backends = { addr = "10.0.0.2"; port = 80; };
};

# 5. 消费数据
den.aspects.haproxy = {
  nixos = { http-backends, lib, ... }: {
    services.haproxy.config = lib.concatMapStringsSep "\n"
      (b: "server ${b.addr} ${b.addr}:${toString b.port}")
      http-backends;
  };
};
```
