# 从其他框架迁移到 Den

## 从纯 NixOS 迁移

如果你已有标准的 NixOS 配置（使用 `lib.nixosSystem` 和配置目录），可以增量迁移到 Den。

### 增量采用策略

Den 完全兼容现有的 NixOS 模块语法。可以逐步迁移，不需要一次性重写所有内容：

```nix
# 第 1 步：在现有 flake 中添加 Den 输入
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    den.url = "github:denful/den";
  };
}
```

### 5 步迁移策略

#### 第 1 步：添加 Den 输入

```nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    home-manager = {
      url = "github:nix-community/home-manager";
      inputs.nixpkgs.follows = "nixpkgs";
    };
    den.url = "github:denful/den";
  };

  outputs = inputs: inputs.den inputs;
}
```

这使用 Den 的 dendritic 模块系统。不需要更改任何 flake 输出。

#### 第 2 步：声明主机

将 `lib.nixosSystem` 调用替换为 Den 的主机声明：

```nix
# modules/hosts.nix 或 defaults.nix
{ den, ... }: {
  # 声明主机
  den.hosts.x86_64-linux.igloo = {
    # 引用方面
    aspect = "igloo";
    users.tux = { };
  };
}
```

Den 会自动为每个主机调用 `lib.nixosSystem`——不再需要手动调用。

#### 第 3 步：使用 import-tree 导入遗留模块

Den 的 `import-tree` 输入可以自动递归导入模块目录：

```nix
{ inputs, ... }: {
  includes = [ (inputs.import-tree inputs.nixpkgs.lib [
    # 递归导入整个配置目录
    ./legacy-modules
  ]) ];
}
```

这让你在逐步提取方面的同时保持现有模块文件不变。

#### 第 4 步：提取方面

将配置提取到方面中。从一个方面开始，为每个主机创建方面：

```nix
# modules/aspects/igloo.nix
{ ... }: {
  den.aspects.igloo = {
    nixos = { pkgs, ... }: {
      # 这是你现有的 NixOS 配置
      boot.loader.systemd-boot.enable = true;
      networking.hostName = "igloo";
      services.openssh.enable = true;
      # ... 更多配置
    };
  };
}
```

#### 第 5 步：移除遗留代码

当所有配置都迁移到方面后，移除：
- 旧的 `lib.nixosSystem` 调用
- 手动 flake 输出定义
- 旧的 `imports = [ ... ]` 文件路径引用

### 对应关系表

| NixOS 概念 | Den 对应概念 |
|---|---|
| `lib.nixosSystem { modules = [...]; }` | `den.hosts.<system>.<name>`——Den 自动调用 nixosSystem |
| `configuration.nix` / 模块文件 | `den.aspects.<name>.nixos`——方面按类打包配置 |
| `imports = [ ./module.nix ]` | `includes = [ den.aspects.foo ]`——类型化引用，不是文件路径 |
| `specialArgs = { ... }` | 参数分发——`{ host, user }: { ... }`——函数参数，不是模块参数 |
| `lib.mkIf condition { ... }` | 上下文形状就是条件——`{ host, user }: ...` 仅在两者都存在时运行 |
| 每主机模块目录 | 方面带按类拥有的配置——一个方面多个平台 |
| `nixos-rebuild switch --flake .#host` | 相同命令——Den 产生标准的 nixosConfigurations |

### Home Manager 对应关系

| Home Manager 概念 | Den 对应概念 |
|---|---|
| `homeManagerConfiguration { modules = [...]; }` | `den.homes.<system>.<name>`（独立）或 `den.hosts.*.users.*.classes = ["homeManager"]`（集成） |
| HM 模块文件 | `den.aspects.<name>.homeManager`——相同模块系统，不同的挂载点 |
| `home-manager switch --flake .#user@host` | 相同命令——Den 产生 homeConfigurations |
| 分离的 HM 和 NixOS 配置 | 一个方面配置两者：`{ nixos = ...; homeManager = ...; }` |

### Flake-parts 对应关系

| Flake-parts 概念 | Den 对应概念 |
|---|---|
| `perSystem` | `den.schema.flake-system`——flake 级策略按系统扇出 |
| `flake.nixosConfigurations` | `den.hosts`——Den 从实体声明生成 flake 输出 |
| `mkFlake` | `inputs.den.flakeModule`——Den 是 flake-parts 模块 |
| `flakeModules` 共享 | `den.ful` 命名空间——可共享的方面库 |

## 从 Flake-parts 迁移

### 逐步替换

Den 与 flake-parts 互补，可以共存：

```nix
{
  inputs = {
    flake-parts.url = "github:hercules-ci/flake-parts";
    den.url = "github:denful/den";
  };

  outputs = inputs:
    inputs.flake-parts.lib.mkFlake { inherit inputs; } {
      # 导入 Den 作为 flake-parts 模块
      imports = [ inputs.den.flakeModules.default ];

      # 现有的 perSystem 代码
      perSystem = { pkgs, ... }: {
        packages.hello = pkgs.hello;
      };

      # Den 主机声明
      den.hosts.x86_64-linux.igloo.aspect = "igloo";
    };
}
```

### 迁移顺序

1. **添加 Den 输入**——Den 作为 flake-parts 模块导入
2. **声明主机**——将 nixosConfigurations 移到 `den.hosts`
3. **提取方面**——将 perSystem 中与主机相关的配置移到方面
4. **清理**——保留 perSystem 用于包、devShells 等

## 迁移注意事项

### 保持不变的内容

- 部署命令不变（`nixos-rebuild`、`home-manager switch`）
- Nix 模块语法在 `nixos = { ... }` 内不变
- Flake inputs、overlays、`pkgs` 工作方式相同
- 所有现有工具（colmena、deploy-rs）兼容

### 不再需要的内容

- 手动 `specialArgs`——用上下文函数参数代替
- 条件 `mkIf`——用上下文形状分发代替
- 手动 flake 输出定义——Den 自动生成
- 路径基础的 `imports`——用方面引用代替

### 需要调整的内容

- `imports` 改为 `includes`（在方面上下文中）
- 文件路径改为方面引用
- 配置按逻辑关注点分组，而不是按目标 OS

## 常见陷阱

### 1. 同时使用 imports 和 includes

迁移过程中可以同时使用两者。Den 的输出导入遗留模块：

```nix
den.aspects.igloo = {
  # 遗留模块（直接从目录导入）
  nixos = { modulesPath, ... }: {
    imports = [
      (modulesPath + "/installer/scan/not-detected.nix")
    ];
    # Den 方面级 include
    includes = [ den.batteries.primary-user ];
  };
};
```

### 2. 条件配置

不要写：

```nix
# 旧方式
{ config, pkgs, ... }: lib.mkIf config.services.xserver.enable {
  services.autorandr.enable = true;
};
```

而写：

```nix
# Den 方式
{ host, ... }: {
  nixos.services.autorandr.enable = true;  # 始终启用
  # 或在需要时拆分到不同方面
};
```

### 3. 特殊参数依赖

不要依赖 `specialArgs`——使用上下文函数参数：

```nix
# 不要：
{ lib, config, ... }: {
  # 这里不能用 host/user
}

# 要：
{ host, user, ... }: {
  nixos = { config, ... }: {
    # 在类模块内部可以安全使用 config
    networking.hostName = host.hostName;
  };
}
```

### 4. 循环引用

方面是真实函数，接收真实数据，不是模块参数。这意味着可以在配置中使用 `host.name` 而不需要 NixOS 模块系统，避免了模块系统依赖循环：

```nix
# 这在 NixOS 模块中可能导致循环：
# services.foo.host = config.networking.hostName;
# 但如果 hostName 依赖 services.foo 呢？

# 这在 Den 中不是问题：
{ host, ... }: {
  nixos.services.foo.host = host.hostName;  # 纯数据，不在模块循环中
}
```

### 5. 类不匹配

确保主机类匹配配置风格：

```nix
den.hosts.aarch64-linux.my-mac = {
  class = "darwin";  # 不是 "nixos"！
};
```
